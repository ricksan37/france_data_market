00 — MODE D'EMPLOI

Comment lire ce manuel

Ce document a deux vies. Aujourd'hui il sert de mémoire externe : reprendre le projet dans deux semaines sans avoir à tout rejouer mentalement. Plus tard il sert de méthode : la prochaine fois qu'un projet data démarre, les patterns ici sont réutilisables tels quels.

Il n'est pas organisé chronologiquement comme un journal. Il est organisé par concept, parce qu'un concept se réutilise et une chronologie ne se réutilise pas.

Les encadrés et ce qu'ils signifient

Théorie

L'idée centrale derrière un pattern. Le pourquoi, pas la syntaxe. Si tu ne dois retenir qu'une chose d'une section, c'est ça.

Décision

Un choix d'architecture assumé, avec sa justification. Ces encadrés reprennent la nomenclature de la spec v1.0 (ÉTABLI, DÉCIDÉ, À MESURER). Ne jamais promouvoir un « À MESURER » en fait sans l'avoir mesuré.

Piège

Une erreur réellement commise pendant la construction, pas une erreur théorique. Le chapitre 10 les regroupe toutes.

Vérifié

Un fait établi par test direct, avec la commande qui le prouve. Le projet a une règle : vérifier plutôt que supposer. Ces encadrés sont la trace de cette règle.

La règle qui gouverne tout le reste

Principe directeur

Le libellé d'une chose ne garantit rien sur son contenu. Un métier ROME nommé « Architecte base de données » contient des architectes navals. Un référentiel officiel Excel diverge de l'API officielle live. Une évidence non testée est une hypothèse déguisée. Teste, ne devine pas.

02 — ARCHITECTURE

L'architecture, du JSON au mart

Les deux outils, et pourquoi ils sont deux

Théorie

DuckDB, c'est le meuble à tiroirs. Une vraie base de données analytique, mais qui tient dans un seul fichier sur le disque. Pas de serveur, pas de Docker, pas de credentials cloud. Un recruteur clone le repo et lance le pipeline en secondes.

dbt, c'est la personne qui trie. On lui écrit des instructions en SQL, et elle les exécute de façon répétable, testable, documentée. dbt ne stocke rien. Il orchestre des transformations et les fait tourner dans le meuble.

DÉCIDÉ — le moteur
CandidatVerdictRaison
SQLiteÉcartéOLTP orienté ligne. Anti-pattern analytique.
PostgreSQLÉcartéClient-serveur, Docker, overhead sans gain à cette échelle.
DuckDBRetenuOLAP colonnaire vectorisé, in-process, lecture JSON et Parquet native. Un projet de 10 modèles sur 400 Mo tourne en ~42 s sur un MacBook.

Les couches, et la règle de dépendance

dbt organise les transformations en couches. La règle est stricte et elle n'est pas cosmétique.

Règle de dépendance

Un modèle staging ne référence jamais un mart. Un mart ne référence jamais directement un autre mart. Le flux va dans un seul sens.

CouchePréfixeRôleStatut
sources — Le JSON brut sur disque. Jamais modifié, jamais en base. Fait
staging stg_ Un modèle par source. Renommage, casting, dédup. Aucune logique métier. Absorbe le risque de dépréciation v2 vers v3. Fait
intermediate int_ Toute la logique métier vit ici. Classification employeur, enrichissement, explosion des skills. À venir
marts fct_ dim_ Les tables exposées à l'analyse. Faits et dimensions. À venir

Pourquoi la couche staging existe vraiment

La documentation France Travail indique qu'une publication d'API v3 déprécie automatiquement la v2. Aucune date annoncée à ce jour.

C'est exactement le rôle de stg_ft_offres. Le jour où le contrat de la source change, un seul modèle est à réécrire. Rien ne se propage en aval. C'est un argument d'architecture à mettre dans le README, pas une faiblesse à cacher.

Le principe directeur du raw

DÉCIDÉ — raw jamais modifié

Les offres extraites de l'API sont déposées telles quelles dans data/raw/. Aucun filtrage, aucun dédoublonnage, aucun enrichissement côté Python.

Toute transformation relève de dbt. Ce découplage garantit qu'on peut rejouer et auditer les transformations sans jamais re-solliciter l'API. Et l'API ne rendrait de toute façon pas le même résultat deux fois, voir chapitre 4.

3.1 — L'authentification OAuth2

Théorie — le flow client_credentials

Il existe plusieurs façons de s'authentifier auprès d'une API. Le flow client_credentials authentifie une application, pas un utilisateur. Il n'y a pas d'écran de connexion, pas de « autorisez-vous cette app à accéder à votre compte ».

Le mécanisme : on échange une fois un client_id et un client_secret contre un token temporaire. Ensuite, seul le token circule, dans le header Authorization: Bearer {token}. Le secret ne repart jamais sur le réseau. Analogie : le badge visiteur qu'on récupère à l'accueil contre une pièce d'identité, et qu'on montre ensuite à chaque porte.

Vérifié par test direct
  • Endpoint token : https://entreprise.francetravail.fr/connexion/oauth2/access_token?realm=/partenaire
  • Grant type : client_credentials
  • Scope : api_offresdemploiv2 o2dsoffre
  • Corps de requête en application/x-www-form-urlencoded, donc le paramètre data= de requests, pas json=
  • Durée de validité mesurée : 1499 secondes, environ 25 minutes. Un refresh est nécessaire au-delà.
Piège — une source tierce disait le contraire

Le site all-api.fr affirmait que certains endpoints étaient accessibles sans authentification. C'est faux. Vérifié contre le wrapper Python officiel sur PyPI et un projet HuggingFace en production : OAuth2 est obligatoire. Première illustration de la règle « vérifier plutôt que supposer », et elle est arrivée avant la première ligne de code.

auth.py
"""
Authentification OAuth2 auprès de l'API France Travail.

Flow : client_credentials. On échange un couple id/secret contre un
token temporaire (~25 min), puis seul le token circule.

Le secret vit dans .env, jamais dans le code, jamais sur GitHub.
"""
import os
import requests
from dotenv import load_dotenv

load_dotenv()  # charge .env dans les variables d'environnement

TOKEN_URL = (
    "https://entreprise.francetravail.fr/connexion/oauth2/access_token"
    "?realm=/partenaire"
)

def get_access_token():
    """
    Récupère un token d'accès valide ~1499 secondes.

    Returns:
        str: le token à placer dans le header Authorization: Bearer {token}

    Raises:
        requests.HTTPError: si l'authentification échoue (401, 403...)
    """
    payload = {
        "grant_type": "client_credentials",
        "client_id": os.getenv("FT_CLIENT_ID"),
        "client_secret": os.getenv("FT_CLIENT_SECRET"),
        "scope": "api_offresdemploiv2 o2dsoffre",
    }

    # POINT CRITIQUE : data= et non json=.
    # L'endpoint attend du application/x-www-form-urlencoded.
    # Avec json= la requête part en application/json et l'API refuse.
    response = requests.post(TOKEN_URL, data=payload)
    response.raise_for_status()

    return response.json()["access_token"]

3.2 — La recherche et la pagination

Théorie — la pagination par offset

Une API ne renvoie jamais des milliers de résultats d'un coup. Elle en donne une tranche, et on redemande la suivante. France Travail utilise la pagination par offset : on demande « les éléments aux positions 150 à 299 » via le header Range: offres=150-299.

Deux détails qui surprennent au début. Le Range est un header de requête, pas un query param dans l'URL. Et la réponse revient en HTTP 206 Partial Content, pas 200. Le 206 n'est pas une erreur, c'est le signal normal d'une réponse paginée partielle. Le total réel se lit dans le header Content-Range, après le slash.

Vérifié par test direct
  • Endpoint : https://api.francetravail.io/partenaire/offresdemploi/v2/offres/search
  • Premier appel motsCles=data analyst → HTTP 206, header Content-Range: offres 0-149/230
  • Par défaut : 150 premières offres, range 0-149
  • Plafond absolu : range max 0-1149, soit 1150 offres maximum par recherche
Le bug corrigé, et sa leçon générale

La condition d'arrêt de la boucle de pagination reposait uniquement sur total, une valeur fournie par le serveur dans Content-Range. Si ce header manque une seule fois, la boucle tourne à l'infini.

Principe retenu, transférable à n'importe quelle boucle sur API : la condition d'arrêt ne doit jamais dépendre uniquement d'une valeur fournie par le serveur. Toujours une borne indépendante, connue à l'avance. Ici max_start = 1149.

search.py
"""
Recherche d'offres sur l'API France Travail, avec pagination.

Contraintes de la source, établies par test :
  - 150 résultats max par appel
  - range max absolu : 0-1149, donc 1150 offres par recherche
  - réponse 206 Partial Content quand il reste des pages
  - l'index est temps réel, donc instable pendant la pagination
"""
import requests
from auth import get_access_token

SEARCH_URL = (
    "https://api.francetravail.io/partenaire/offresdemploi/v2/offres/search"
)

PAGE_SIZE = 150       # imposé par l'API
MAX_START = 1149      # plafond absolu, borne indépendante du serveur


def search_offres(params, token, start=0, end=149):
    """
    Un appel unique à l'endpoint de recherche.

    Args:
        params (dict): critères de recherche (motsCles, codeROME...)
        token (str): access token OAuth2
        start (int): position du premier élément voulu
        end (int): position du dernier élément voulu

    Returns:
        requests.Response: la réponse brute, pour lire le body ET les headers
    """
    headers = {
        "Authorization": f"Bearer {token}",
        # Range est un HEADER, pas un query param.
        "Range": f"offres={start}-{end}",
    }
    response = requests.get(SEARCH_URL, headers=headers, params=params)
    response.raise_for_status()
    return response


def get_all_offres(params, token=None):
    """
    Récupère toutes les offres d'une recherche, en paginant.

    Args:
        params (dict): critères de recherche
        token (str, optional): token réutilisable. Si None, en demande un.
            Permet de partager un seul token entre plusieurs recherches
            plutôt que de se ré-authentifier à chaque fois.

    Returns:
        list[dict]: les offres brutes, doublons INCLUS.

    Note:
        Le dédoublonnage n'est PAS fait ici. C'est la responsabilité de
        stg_ft_offres en dbt (spec §7.2). Filtrer ici serait une dérive
        silencieuse d'architecture.
    """
    if token is None:
        token = get_access_token()

    toutes_offres = []
    start = 0

    while start <= MAX_START:   # borne indépendante, JAMAIS le total serveur seul
        end = min(start + PAGE_SIZE - 1, MAX_START)

        response = search_offres(params, token, start=start, end=end)
        resultats = response.json().get("resultats", [])

        if not resultats:
            break   # plus rien à récupérer

        toutes_offres.extend(resultats)

        # 200 signifie "réponse complète", donc pas de page suivante.
        # 206 signifie "il en reste".
        if response.status_code == 200:
            break

        start += PAGE_SIZE

    return toutes_offres

3.3 — L'orchestration du pull

Six catégories à interroger, un seul token à partager, un dump horodaté à produire avec sa traçabilité.

DÉCIDÉ — l'objet metadata dans le dump

Le fichier JSON produit a deux blocs : metadata et resultats.

metadata capture l'état du pipeline au moment T, pas seulement l'état du marché. Quelle requête, quand, dans quelles conditions, combien de doublons. Sans ça, impossible de savoir six mois plus tard si un écart de volume vient du marché ou d'un changement de code.

Implication directe pour dbt : le lecteur en aval doit cibler resultats, pas la racine du fichier. C'est exactement ce que fait le chapitre 7.

DÉCIDÉ — pas de champ categorie_source injecté dans les offres

Tentation naturelle : ajouter un champ à chaque offre pour savoir de quelle recherche elle vient. Refusé. Ça violerait « raw jamais modifié ». Les comptes par catégorie vivent dans metadata, pas dans les offres. Le prix à payer : on ne peut pas retracer la catégorie d'origine d'une offre donnée. C'est assumé.

pull_complet.py
"""
Orchestration du pull complet sur les 6 catégories du périmètre.

Produit data/raw/offres_AAAA-MM-JJ_HHMM.json avec deux blocs :
  - metadata : traçabilité de la collecte
  - resultats : les offres brutes, jamais modifiées

Le dédoublonnage est MESURÉ et LOGUÉ ici, mais PAS APPLIQUÉ.
Il appartient à stg_ft_offres en dbt (spec §7.2).
"""
import json
from datetime import datetime
from pathlib import Path

from auth import get_access_token
from search import get_all_offres

# Périmètre arrêté en session 1, après test direct de chaque code ROME.
# Stratégie HYBRIDE : codeROME quand le métier ROME est dédié à la data,
# motsCles quand il est fourre-tout. Voir chapitre 4 du manuel.
CATEGORIES = [
    {"nom": "data_scientist",       "params": {"codeROME": "M1405"}},
    {"nom": "data_engineer",        "params": {"codeROME": "M1811"}},
    {"nom": "data_analyst",         "params": {"motsCles": "data analyst"}},
    {"nom": "data_architect",       "params": {"motsCles": "data architect"}},
    {"nom": "decisionnel",          "params": {"motsCles": "décisionnel"}},
    {"nom": "business_intelligence", "params": {"motsCles": "business intelligence"}},
]

OUTPUT_DIR = Path("data/raw")


def pull_complet():
    """
    Interroge les 6 catégories et écrit un dump horodaté.

    Un SEUL token est demandé puis partagé entre les 6 recherches.
    Se ré-authentifier 6 fois serait inutile : le token vaut 25 minutes,
    largement assez pour l'ensemble du pull.
    """
    token = get_access_token()

    toutes_offres = []
    comptes = {}

    for categorie in CATEGORIES:
        offres = get_all_offres(categorie["params"], token=token)

        # Mesure des doublons INTERNES à cette catégorie.
        # Cause : pagination par offset sur un index temps réel.
        # On mesure, on ne filtre pas. La spec §11 Phase 1 demande
        # explicitement de "mesurer le volume réel par métier".
        ids = [o["id"] for o in offres]
        ids_uniques = set(ids)

        comptes[categorie["nom"]] = {
            "params": categorie["params"],
            "brutes": len(offres),
            "uniques": len(ids_uniques),
            "doublons_internes": len(offres) - len(ids_uniques),
        }

        print(
            f"{categorie['nom']:24} "
            f"brutes={len(offres):5} "
            f"uniques={len(ids_uniques):5} "
            f"doublons={len(offres) - len(ids_uniques):5}"
        )

        toutes_offres.extend(offres)

    # Comptes globaux, tous doublons confondus (intra + inter catégories)
    ids_globaux = [o["id"] for o in toutes_offres]
    uniques_globaux = set(ids_globaux)

    dump = {
        "metadata": {
            "date_extraction": datetime.now().isoformat(),
            "source": "API France Travail Offres d'emploi v2",
            "categories": comptes,
            "total_brutes": len(toutes_offres),
            "total_uniques": len(uniques_globaux),
            "total_doublons": len(toutes_offres) - len(uniques_globaux),
        },
        "resultats": toutes_offres,   # BRUT. Jamais modifié.
    }

    OUTPUT_DIR.mkdir(parents=True, exist_ok=True)
    horodatage = datetime.now().strftime("%Y-%m-%d_%H%M")
    chemin = OUTPUT_DIR / f"offres_{horodatage}.json"

    with open(chemin, "w", encoding="utf-8") as f:
        json.dump(dump, f, ensure_ascii=False, indent=2)

    print(f"\n{len(toutes_offres)} offres brutes, "
          f"{len(uniques_globaux)} uniques → {chemin}")


if __name__ == "__main__":
    pull_complet()
04 — PHASE 1

Les quatre découvertes

Ces quatre découvertes sont la vraie matière portfolio de la Phase 1. Aucune n'était dans le plan initial. Chacune est arrivée parce qu'un test a contredit une supposition.

Découverte 1 — L'index de recherche est instable

Symptôme observé

300 offres récupérées, 151 ID uniques. Puis, quelques minutes plus tard, le même script retourne 450 offres. Le total déclaré par l'API est passé de 230 à 300 entre deux exécutions.

Diagnostic, vérifié sur la doc officielle

L'API restitue les offres en temps réel. La pagination par offset (range=150-299 signifie « donne-moi les éléments à ces positions ») suppose implicitement un index figé.

Si des offres sont ajoutées ou retirées entre deux appels, les positions ne pointent plus vers les mêmes éléments. Résultat : chevauchement entre pages, et donc doublons. Aucun paramètre de tri stable documenté n'a été trouvé pour figer l'ordre.

Les doublons mesurés, par catégorie

Le pattern est net : les doublons n'apparaissent que dès qu'il y a plus d'une page. Une seule page, pas de pagination, pas de chevauchement, zéro doublon. C'est cohérent avec le diagnostic, et c'est ce qui le confirme.

Les ~93 doublons inter-catégories sont d'une autre nature, et ils sont attendus. Hypothèse principale : « décisionnel » et « business intelligence » se recoupent fortement. Une offre « Consultant décisionnel - Business Intelligence » matche les deux recherches. Quantifiable précisément une fois en dbt.

DÉCIDÉ — ne pas dédoublonner dans l'ingestion

La spec §7.2 assigne explicitement cette responsabilité à stg_ft_offres. Ajouter un filtre dans le script Python aurait été une dérive silencieuse d'architecture : une décision prise dans le feu de l'action, contraire à une décision documentée, et jamais tracée nulle part.

Le script mesure et logue les doublons, conforme à la Phase 1 (« Mesurer : volume réel par métier »). Il ne les filtre pas.

Ce que ça donne en entretien

« J'ai mesuré 66 % de doublons sur une catégorie », et l'explication : pagination par offset sur un index temps réel. Ça montre qu'on comprend pourquoi ça casse, pas juste qu'on l'a patché.

Découverte 2 — Le libellé ROME ne garantit pas le contenu

Le plan initial prévoyait 4 mots-clés : data analyst, data engineer, data scientist, analytics engineer. Cette approche a été challengée et remplacée.

Problème du motsCles : c'est du texte libre. Ça matche n'importe où, sans garantie d'exhaustivité ni de précision.

Théorie — le référentiel ROME

ROME 4.0 est la taxonomie métier officielle de France Travail. 14 grands domaines, 110 domaines professionnels, 532 métiers, 14 301 appellations. Chaque offre porte nativement romeCode et romeLibelle.

Passer de motsCles à codeROME n'était pas une nouvelle décision. La spec §5.3 avait déjà tranché que le ROME est la taxonomie officielle pour le métier. C'était l'application d'une décision existante.

05 — PHASE 2.1

Initialiser dbt-duckdb

Où on en est dans la spec

Phase 1 a laissé un dump JSON et rien pour le lire. Avant d'écrire le moindre modèle, il faut un projet dbt qui sache où est le moteur (le fichier DuckDB) et où sont les modèles. Pas de SQL à cette étape. L'objectif unique est un dbt debug qui répond vert.

Les deux fichiers de config

Théorie — pourquoi deux fichiers et pas un

dbt sépare volontairement deux choses.

dbt_project.yml décrit ce que fait le projet : nom, où sont les modèles, comment ils se matérialisent. Versionné, public, identique pour tout le monde.

profiles.yml décrit à quelle base on se connecte : type d'adapter, chemin, credentials. Historiquement placé dans ~/.dbt/, hors du repo, parce que ça contient des mots de passe.

Analogie : dbt_project.yml est la recette. profiles.yml est l'adresse de la cuisine.

DÉCIDÉ — profiles.yml dans le repo, pas dans ~/.dbt/

DuckDB n'a pas de credentials. C'est un fichier local. Donc profiles.yml peut vivre dans le repo, versionné.

Ça sert directement l'argument spec §7.1 : le recruteur clone et lance, sans setup. Depuis dbt 1.5, dbt cherche profiles.yml dans le répertoire courant avant ~/.dbt/. Ce choix serait faux sur Snowflake ou BigQuery, où le fichier contient des secrets. Il est correct ici parce que la base est un fichier.

06 — PHASE 2.2

Déclarer la source

Où on en est

dbt tourne mais il ne « voit » pas le JSON. Il faut lui dire où regarder, et surtout vérifier la vraie forme des données plutôt que la supposer. Le compte rendu de Session 1 annonçait la structure {metadata, resultats}. On le confirme nous-mêmes.

Théorie — les sources dbt

Une source en dbt est une déclaration : « cette donnée existe, je ne la construis pas, mais mes modèles en dépendent ». Ça se déclare en YAML, avec un nom, et on la référence dans un modèle via {{ source('nom', 'table') }}.

Particularité DuckDB : DuckDB lit un fichier JSON directement, sans étape de chargement. Pas de COPY INTO, pas de script d'import. dbt-duckdb exploite ça : on donne une fonction DuckDB (read_json_auto(...)) au lieu d'un simple nom de table. dbt remplace {{ source(...) }} par cet appel de fonction à la compilation.

observatoire/models/staging/_sources.yml
version: 2

sources:
  - name: raw
    # external_location remplace le nom de table par une fonction DuckDB.
    # read_json_auto infère automatiquement le schéma du fichier.
    # Chemin relatif à observatoire/, d'où le ../
    meta:
      external_location: "read_json_auto('../data/raw/offres_2026-07-17_1403.json')"
    tables:
      - name: ft_offres
observatoire/models/staging/stg_ft_offres.sql — v1, lecture brute
select * from {{ source('raw', 'ft_offres') }}
Théorie — Jinja, et pourquoi les doubles accolades

{{ }} est la syntaxe Jinja, le moteur de templating que dbt exécute avant d'envoyer quoi que ce soit à la base.

Sans les accolades, dbt ne sait pas que c'est une instruction pour lui. Il laisse passer le texte tel quel vers DuckDB, qui reçoit source('raw', 'ft_offres') et répond Catalog Error: Table Function with name source does not exist!. Parce que c'est vrai : source() n'existe dans aucun dialecte SQL. C'est un mot à dbt, pas à la base.

Piège — le linter SQL de VS Code hurle au faux positif

VS Code affiche Incorrect syntax near '{'. Expecting ID. sur la ligne {{ source(...) }}.

C'est une extension SQL générique (ici configurée pour MSSQL) qui valide le fichier avant que dbt n'entre en jeu. Elle ne connaît pas Jinja. Faux positif. Le réflexe naturel est de retirer les accolades pour faire taire le warning, ce qui casse tout. La seule source de vérité est la sortie du terminal, pas le soulignement rouge de l'éditeur.

Le problème

Théorie — UNNEST

Imagine une étagère avec une seule case, et dans cette case un sac contenant 1094 fiches. UNNEST sort chaque fiche et lui donne sa propre case.

Techniquement : UNNEST transforme une colonne de type tableau en plusieurs lignes, une par élément. Les autres colonnes de la ligne d'origine (ici metadata) se retrouveraient dupliquées sur chaque nouvelle ligne si on les gardait dans le SELECT. C'est pour ça qu'on ne les garde pas.

Le piège du nommage

Dès qu'on essaie de piocher un sous-champ avec offre.id, ça casse :

Binder Error: Table "offre" does not have a column named "id"
Candidate bindings: : "unnest"
Théorie — table vs colonne dans un unnest

Quand on écrit unnest(resultats) as offre dans la clause FROM, DuckDB comprend as offre comme le nom de la table virtuelle produite, pas comme le nom de la colonne qu'elle contient.

La colonne existe, mais elle porte un nom généré automatiquement (unnest). Donc offre.id cherche une colonne id sur une table qui n'a pas cette forme. Le message d'erreur le dit d'ailleurs : Candidate bindings: : "unnest", c'est le seul nom que DuckDB connaît.

La solution : la syntaxe as t(offre). Elle dit « la table virtuelle s'appelle t, et sa seule colonne s'appelle offre ». C'est cette colonne qui contient le STRUCT, donc offre.id redevient valide.

-- casse
from {{ source('raw', 'ft_offres') }}, unnest(resultats) as offre

-- marche
from {{ source('raw', 'ft_offres') }}, unnest(resultats) as t(offre)

Le dédoublonnage

Théorie — ROW_NUMBER() et QUALIFY

Technique standard pour dédupliquer en SQL analytique. Deux temps.

1. Numéroter dans chaque groupe. row_number() over (partition by offre_id order by date_actualisation desc) dit : « pour chaque offre_id, classe les lignes de la plus récente à la plus ancienne, et numérote-les 1, 2, 3... ». partition by définit le groupe, order by définit qui est numéro 1.

2. Ne garder que le numéro 1. qualify rn = 1 filtre. QUALIFY est à une fonction fenêtre ce que HAVING est à un GROUP BY : un filtre qui s'applique après le calcul. Sans lui, il faudrait une sous-requête entière juste pour filtrer sur rn.

Pourquoi trier par date_actualisation desc et pas au hasard ? Parce que si une offre a été modifiée entre deux pages récupérées, et l'index bouge en temps réel donc c'est possible, la version la plus récente est la plus fiable. Ce tri est une décision, pas un détail.

Théorie — commit n'est pas push

git commit sauvegarde un instantané en local, sur le disque. GitHub n'en sait rien. git push envoie l'historique local vers le dépôt distant. Entre les deux, on peut commiter autant qu'on veut sans rien exposer. C'est ce qui rend le chapitre suivant possible.

Réécrire l'historique, tant que rien n'est poussé

Cas réel : le premier commit contenait docs/*.gdoc, des pointeurs Google Drive illisibles hors du Drive. Deux façons de traiter ça, et il faut savoir laquelle on veut.

BesoinAction
A. Que git arrête de suivre ces fichiers désormais Ajouter au .gitignore. Suffit. Mais les fichiers restent dans les commits passés, gelés à cet état.
B. Qu'ils disparaissent aussi de l'historique Réécrire le commit. Plus délicat, et impossible sans casse une fois poussé. 
# Option B, sur le dernier commit, avant tout push

# 1. retirer du suivi git, MAIS garder les fichiers sur le disque
git rm -r --cached docs/

# 2. ignorer désormais
echo "docs/" >> .gitignore

# 3. vérifier ce qui va changer AVANT d'écraser
git status

# 4. amender : réécrit le commit existant au lieu d'en empiler un nouveau
git add .gitignore
git commit --amend

# 5. confirmer
git log --stat
Théorie — pourquoi amend plutôt qu'un nouveau commit

Un commit « ajout des docs » suivi d'un commit « suppression des docs » raconte une histoire inutile et laisse les fichiers dans l'historique. --amend réécrit le commit comme s'il avait toujours été correct. C'est sans danger tant que rien n'a été poussé : personne d'autre n'a cette version, donc personne ne se retrouve avec un historique divergent. Après un push, c'est une autre affaire.

Piège — git rm --cached ne supprime pas le fichier

Le --cached est essentiel. Il retire le fichier de l'index git, pas du disque. Sans lui, git rm supprime pour de bon. Le git status affiche alors deleted:, ce qui est correct et ne veut pas dire que le fichier a disparu du disque.

11 — MÉTHODE

Méthode réutilisable pour le prochain projet

Ce qui précède est spécifique à France Travail. Ce qui suit ne l'est pas.

Les six principes, dans l'ordre d'importance

01

Le libellé ne garantit pas le contenu

Un métier ROME « Architecte base de données » contient des architectes navals. Un référentiel Excel officiel diverge de l'API officielle. Un champ nommé entreprise.nom est vide la moitié du temps. Chaque fois qu'un nom laisse supposer un contenu, tester ce contenu. Le coût du test est de quelques minutes. Le coût d'une supposition fausse se paie sur toute la chaîne en aval.

02

Une boucle ne s'arrête jamais sur une valeur du serveur seule

Toujours une borne indépendante, connue à l'avance. Le serveur peut omettre un header, changer un total, renvoyer une réponse partielle. Valable pour toute pagination, tout retry, tout polling.

03

Le raw ne se modifie jamais

Aucun filtrage, aucun enrichissement, aucun dédoublonnage à l'ingestion. Deux raisons. On peut rejouer et auditer les transformations sans re-solliciter la source. Et une source vivante ne rendra jamais deux fois le même résultat, donc le dump est la seule vérité reproductible.

04

Chaque responsabilité à sa couche, et pas d'exception « juste cette fois »

Le dédoublonnage appartenait à dbt. L'ajouter dans le script Python aurait pris trois lignes et « marché ». C'est ça, une dérive silencieuse : une décision prise dans le feu de l'action, contraire à une décision documentée, jamais tracée. Six mois plus tard, personne ne sait plus où vit la logique. Si une décision de la spec doit être rouverte, la rouvrir explicitement et argumenter.

05

Mesurer et exposer, plutôt que filtrer et taire

66 % de doublons n'est pas un problème à cacher, c'est une caractéristique de la source à documenter. La moitié des employeurs masqués n'est pas un échec de collecte, c'est le résultat central du projet. Un taux d'échec exposé vaut mieux qu'un taux d'échec dissimulé, en portfolio comme en production.

06

Vérifier à chaque étape, avec un chiffre attendu

1094 après le UNNEST. 552 après le QUALIFY. Chaque étape a un nombre qu'on peut prédire et confronter. Sans ça, une erreur silencieuse se propage sur dix modèles avant qu'on la voie.

L'ordre de construction d'un modèle staging

Ne jamais écrire le modèle complet d'un coup. Chaque palier a une erreur possible, et on veut savoir laquelle.

  1. Lire brut — select *. Voir ce qui arrive vraiment.
  2. Aplatir — unnest. Vérifier le compte.
  3. Inventorier — typeof. Choisir les champs sur pièces, pas de mémoire.
  4. Extraire 3 ou 4 champs — valider la mécanique avant de faire les 14.
  5. Extraire tout, caster, renommer — snake_case partout.
  6. Dédupliquer — qualify row_number(). Vérifier le compte final.
  7. Nettoyer — supprimer les modèles d'exploration jetables.
  8. Committer — un commit par palier stable.

Quand committer

À chaque état stable et compréhensible. Ni à chaque ligne, ni seulement en fin de journée. Le test : si ce commit est montré à quelqu'un d'autre, est-ce que le message et le diff racontent une histoire cohérente ?

Tests dbt et un bug DuckDB

Point 0 de la Phase 2, qualifié « jour 1 » par la spec (§8.1) mais jamais fait en Session 2 : combler les tests manquants sur stg_ft_offres. Cette étape, en apparence la plus simple de la session, a occupé la majeure partie du temps — pas à cause des données, à cause d'un bug interne du moteur.

Schema tests, en une phrase

Théorie

Un schema test ne décrit pas comment vérifier, il décrit quelle propriété doit être vraie. dbt génère lui-même une requête qui cherche les lignes qui violent la règle. 0 ligne trouvée = pass. C'est l'inverse de l'intuition : le test réussit quand la requête ne ramène rien.

models/staging/stg_ft_offres.ymlcolumns:
  - name: offre_id
    data_tests:
      - unique
      - not_null
  - name: type_contrat
    data_tests:
      - accepted_values:
          values: ['CDI', 'CDD', 'MIS', 'LIB']

data_tests: et non tests: — l'ancien nom est déprécié depuis dbt 1.8. Les deux marchent encore, mais le premier est le nom courant sur dbt-core 1.11.

Une donnée qui apprend quelque chose : CCE

Vérifié

Le test accepted_values sur type_contrat échoue : 1 ligne hors de la liste des 4 valeurs connues. Distribution vérifiée par GROUP BY plutôt que supposée → CCE, un Contrat de Coopération de l'Emploi, lié aux coopératives d'activité et d'emploi. Légitime, marginal, absent de la spec initiale. La liste a été élargie plutôt que la ligne supprimée : un test qui fail est une découverte sur la donnée, pas un bug à masquer.

Le bug DuckDB, isolé

Une fois CCE ajouté, le même test échoue de nouveau — mais différemment : ERROR au lieu de FAIL, avec une stack trace C++ et un message INTERNAL Error: Attempted to access index 4 within vector of size 4.

Piège

Ce n'est pas un fail (une requête qui trouve des lignes fautives), c'est une InternalException — le moteur lui-même s'effondre pendant l'optimisation. La cause ne peut être ni la donnée ni la logique métier.

Méthode d'isolation : reproduire la même requête hors dbt, directement en DuckDB/Python. Elle plante à l'identique. Preuve que ni dbt, ni la macro accepted_values, ni les données ne sont en cause — seul le moteur DuckDB, sur toute expression IN(...) / NOT IN(...) à plusieurs valeurs (observé à partir de 5), une fois qu'une vue qui en contient une est interrogée.

Tentative de résolution par upgrade du moteur — deux faux départs avant d'y arriver : une installation accidentelle d'un méta-paquet dbt 2.0.0rc200 vide (mauvaise cible d'un --pre), puis la découverte que dbt et python3 pointent vers deux interpréteurs Python distincts.

# l'interpréteur qui compte n'est pas celui de "which python3"
which dbt
head -1 $(which dbt)          # le shebang révèle le vrai interpréteur
# installer dans CET interpréteur précis, pas un autre
/usr/local/bin/python3 -m pip install --upgrade "duckdb>=1.5"
Résultat, après upgrade vers DuckDB 1.5.4

Le bug persiste. Confirmé version-indépendant, pas un simple retard de patch. Contournement retenu, systématique pour la suite du projet : remplacer tout IN()/NOT IN() par des chaînes de =/!= reliées par OR/AND.

Le test singulier, la porte de sortie

Théorie

Un schema test est une macro générique, paramétrée depuis le YAML. Un test singulier est l'inverse : un simple fichier .sql dans tests/, dont on écrit soi-même la requête. Même contrat dbt (0 ligne = pass), mais on contrôle entièrement le SQL généré — la seule option quand une macro générique produit un SQL qui casse le moteur.

tests/assert_type_contrat_valide.sqlselect
    offre_id,
    type_contrat
from {{ ref('stg_ft_offres') }}
where type_contrat != 'CDI'
  and type_contrat != 'CDD'
  and type_contrat != 'MIS'
  and type_contrat != 'LIB'
  and type_contrat != 'CCE'

Avoir des tests répartis entre YAML (génériques) et tests/ (singuliers) n'est pas une incohérence — c'est le cas d'usage normal du test singulier : le bon outil pour une règle sur mesure, ou pour celle qu'une macro générique ne peut pas exprimer sans casser.

Piège — à ne jamais oublier

colonne != valeur ignore silencieusement les lignes NULL : en SQL, NULL != 'CDI' ne vaut pas true, il vaut NULL (inconnu). Sur ce projet ça ne change rien (aucune valeur NULL dans les colonnes testées), mais c'est le genre de détail qui fait qu'un test « passe » en ratant des cas.

La couche intermediate, en une phrase

Théorie

Staging nettoie sans transformer. Les marts sont le produit fini. Entre les deux, int_ fait le travail sale : parsing, jointures d'enrichissement, classifications. Analogie : staging = ingrédients lavés, int_ = cuisine, marts = plat dressé.

Le parsing salaire

Exploration avant toute regex : 380 offres sur 552 sans salaire_libelle, 172 renseignées. Répartition par préfixe — Annuel 146, Mensuel 25, Horaire 1 — un 3e préfixe non couvert par les fixtures de la spec (§8.2), découvert par inspection directe plutôt que supposé absent.

(Annuel|Mensuel|Horaire) de (\d+(?:\.\d+)?) Euros(?: à (\d+(?:\.\d+)?) Euros)?

Regex à 3 groupes captants — période, montant 1, montant 2 optionnel — validée isolément en Python pur avant intégration SQL. Méthode : ne pas mélanger l'inconnue « la regex fonctionne-t-elle » avec l'inconnue « la syntaxe SQL est-elle correcte ».

models/intermediate/int_offres_salaire.sql (extrait)with extraction as (
    select
        offre_id,
        regexp_extract(salaire_libelle, '(Annuel|Mensuel|Horaire) de (\d+(?:\.\d+)?) Euros(?: à (\d+(?:\.\d+)?) Euros)?', 1) as periode_texte,
        regexp_extract(salaire_libelle, '(Annuel|Mensuel|Horaire) de (\d+(?:\.\d+)?) Euros(?: à (\d+(?:\.\d+)?) Euros)?', 2) as montant_1_texte,
        regexp_extract(salaire_libelle, '(Annuel|Mensuel|Horaire) de (\d+(?:\.\d+)?) Euros(?: à (\d+(?:\.\d+)?) Euros)?', 3) as montant_2_texte
    from {{ ref('stg_ft_offres') }}
),
converti as (
    select
        offre_id,
        periode_texte as salaire_periode_brute,
        cast(cast(nullif(montant_1_texte, '') as double) as integer) as salaire_min,
        cast(cast(nullif(montant_2_texte, '') as double) as integer) as salaire_max_brut
    from extraction
)
-- select final : coalesce(salaire_max_brut, salaire_min) pour le cas sans fourchette

Un regexp_extract sans correspondance renvoie une chaîne vide '', pas NULL. ''::INTEGER plante en cast direct. NULLIF(valeur, '') convertit la chaîne vide en NULL avant le cast.

Le unit test, given / expect

Théorie

Analogie : un schema test contrôle la production réelle, un unit test est un banc d'essai en atelier avec des pièces factices dont on connaît la réponse à l'avance.
